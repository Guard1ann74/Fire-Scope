# Fire Scope — сервис: установка, параметры, API

Веб-интерфейс и REST API мониторинга природных пожаров. Сервис работает только на
реальных источниках, встроенных демонстрационных данных нет. По умолчанию он
работает в режиме «огонь прежде гари»: ищет подтверждённые очаги огня NASA FIRMS
(VIIRS) в выбранной области и периоде и оценивает гарь только вокруг них по паре
снимков Sentinel-2 до и после (Copernicus Data Space). Без ключей сервис честно
сообщает, что источник не настроен, и ничего не рисует.

Пользователь выделяет на карте прямоугольник или полигон, задаёт интервал дат и
получает события огня, контуры гари по степеням, аналитическую справку и выгрузки
в GeoJSON / JSON / CSV / KML. Всё то же самое доступно через REST без интерфейса.

Область можно сохранить без входа на время текущей вкладки или в учётной записи.
Отдельным слоем доступны оперативные детекции NASA FIRMS с задержкой около трёх
часов; районы наблюдения с оповещениями — колокольчик справа (раздел «Мониторинг
огня»).

Прежний режим — модель гари по всему участку без проверки огня — доступен с
`fire_first: false` в запросе (участок до четырёх плиток 10 × 10 км, период до 31
дня). Он принимает за гарь убранные поля; в интерфейсе используется только для
кнопки «Сравнить».

Переключатель `service.use_external_apis` в конфиге модели (`configs/burn_model.yaml`)
читается при запуске сервера. `false` отключает Copernicus и NASA FIRMS; тогда карта
показывает только заранее подготовленные прогнозы из каталога `--data-dir` /
`FIRES_DATA_DIR` (без него сервис не запустится). Переменная `FIRES_QUERY_MODE` может
временно переопределить режим (`archive` или `satellite`).

## Установка

Нужен Python 3.12 или 3.13. Все команды выполняются из корня репозитория.

PowerShell (Windows):

```powershell
cd путь\к\Fire-Scope
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

bash (Linux, macOS):

```bash
cd путь/к/Fire-Scope
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Git Bash на Windows — тот же bash, но venv раскладывается по-виндовому,
исполняемые файлы лежат в `Scripts`, а не в `bin`:

```bash
.venv/Scripts/python -m pip install -r requirements.txt
```

Активировать окружение не обязательно: вызов интерпретатора по пути внутри `.venv`
сам подхватывает нужные пакеты. Если всё-таки нужно — в PowerShell это
`.\.venv\Scripts\Activate.ps1`, в bash `source .venv/bin/activate`
(`source .venv/Scripts/activate` в Git Bash на Windows).
Команды `source` в PowerShell нет.

## Запуск

PowerShell:

```powershell
.venv\Scripts\python.exe -m service
```

bash (Linux, macOS):

```bash
.venv/bin/python -m service
```

Git Bash на Windows:

```bash
.venv/Scripts/python -m service
```

Открыть <http://127.0.0.1:8080/>. Интерактивная документация API — <http://127.0.0.1:8080/docs>.

С активированным окружением достаточно `python -m service`. Равнозначный вариант
запуска — `uvicorn service.app:app --port 8080`.

Если появилась ошибка `Could not open requirements file` или `No module named service` —
команда выполняется не из корня репозитория. Проверить: рядом должны лежать
`requirements.txt`, каталоги `configs/` и `service/`.

Ключи командной строки:

| ключ | по умолчанию | назначение |
|---|---|---|
| `--host` | `127.0.0.1` | адрес прослушивания |
| `--port` | `8080` | порт сервиса |
| `--data-dir` | — | каталог GeoJSON подготовленных прогнозов; включает режим `archive` |
| `--reload` | — | перезапуск при правке кода |

Переменные окружения:

| переменная | по умолчанию | назначение |
|---|---|---|
| `FIRES_HOST`, `FIRES_PORT` | `127.0.0.1`, `8080` | адрес прослушивания |
| `FIRES_QUERY_MODE` | из конфига модели | `satellite` — снимки и модель; `archive` — готовые GeoJSON |
| `FIRES_DATA_DIR` | — | каталог GeoJSON, обязателен в режиме `archive` |
| `FIRES_MODEL_CONFIG` | `configs/burn_model.yaml` | правило гари: предобработка, модель, параметры |
| `FIRES_SERVICE_CONFIG` | `configs/service.yaml` | параметры «огонь прежде гари», снимков, мониторинга |
| `FIRES_MONITOR` | `1` | `0` выключает фоновый опрос FIRMS по районам наблюдения |
| `FIRES_BUILD_MASK` | `1` | `0` не строить отсутствующую маску постоянных источников при запуске |
| `FIRES_SATELLITE_CACHE` | `artifacts/satellite-cache` | кеш DEM и WorldCover для модели |
| `CDSE_CLIENT_ID`, `CDSE_CLIENT_SECRET` | `.secrets/cdse.env` | OAuth-клиент Copernicus Process API |
| `FIRES_DB` | `service/data/service.sqlite3` | база учётных записей и областей |

| `FIRES_LLM_MODEL` | `deepseek-flash` / `gpt-4o-mini` | модель выбранного провайдера |
| `FIRES_LIVE_DAYS` | `2` | глубина запроса к FIRMS в сутках, предел API — 5 |
| `FIRES_SECURE_COOKIES` | `false` | ставить флаг Secure на куку сессии (только под HTTPS) |

Для включения ИИ-разбора добавьте на сервере файл `.secrets/llm.env` с одной строкой
`DEEPSEEK_API_KEY=ваш_ключ` (или задайте переменную окружения), затем перезапустите
сервис. Для OpenAI задайте `FIRES_LLM_PROVIDER=openai` и `OPENAI_API_KEY`.
В подробной аналитике области пояснение появится первым, перед показателями;
кнопка «Повторить» позволяет повторить неудачный запрос. Без ключа карточка
скрыта, а графики и показатели доступны. Внешнему
провайдеру передаются только агрегированные числа, динамика по годам и месяцам
и период запроса — без снимков, координат и имён пользователей. На основе
многолетних данных модель может дать осторожный сезонный ориентир. Ключ отправляется
провайдеру сервером и не попадает в браузер. Запросы
ограничены пятью в минуту на адрес клиента, одинаковые результаты кешируются
на десять минут; использование внешнего API может тарифицироваться провайдером.

## Как пользоваться интерфейсом

1. **Область.** «Прямоугольник» — два клика по противоположным углам. «Полигон» —
   клики по вершинам, замкнуть по первой точке, кнопкой «Замкнуть» или `Enter`;
`Esc` отменяет. «Взять экран карты» берёт текущие границы вида; в режиме ML
   сначала приблизьте карту до участка не больше 60 км по стороне. Готовую область
   можно перетащить за середину, изменить за углы или вершины. Кнопку над
   областью можно потянуть для поворота: кнопка остаётся у верхней границы
   фигуры и движется только вместе с ней. `Delete` удаляет выбранную область.
   После правки нажмите «Показать пожары» ещё раз.
2. **Период.** Поля дат или пресеты. Для сохранённых данных при старте
   подставляется весь доступный период. В спутниковом режиме подставляется
   недавний двухнедельный период события.
3. **«Показать пожары».** Карта заполняется, справа появляется справка.
4. **Клик по объекту.** У термоточки — дата и спутник (плюс прибор, достоверность, FRP).
   У контура — идентификатор, степень поражения, площадь в гектарах, дата начала
   пожара, даты снимков и подтверждение огнём.
5. **Слои и легенда** — слева: термоточки, контуры, граница области; цвета степеней
   с площадью по каждой.
6. **Выгрузка** — четыре кнопки внизу справа.
7. **Наблюдение.** «Сохранить текущую область» доступно без входа. Для гостя
   область хранится в `sessionStorage` этой вкладки и исчезает после её закрытия;
   после входа области сохраняются в аккаунте. Сохранённая область открывается
   одним кликом: восстанавливаются геометрия и период, запрос выполняется сразу,
   а над справкой появляется «Что изменилось» с прошлого просмотра.

Состояния интерфейса: загрузка (спиннер), ошибка (текст ошибки от API + кнопка
«Повторить»), «ничего не найдено» (когда в области за период нет ни одного объекта).

## Огонь прежде гари

Режим включён по умолчанию (`configs/service.yaml`, `fire_first.enabled`). Модель
гари обучалась на снимках, заранее выбранных вокруг известных пожаров; на
произвольном участке она принимает за гарь убранные и вспаханные поля. Поэтому
сервис сначала ищет доказательство огня и только потом оценивает гарь:

1. **Термоточки.** NASA FIRMS Area API, спутники VIIRS SNPP, NOAA-20, NOAA-21 за
   период запроса окнами по 5 суток. Набор (архив SP или оперативный NRT)
   выбирается по `data_availability` FIRMS для каждой даты.
2. **Фильтры.** Не считаются доказательством: точки с низкой достоверностью
   (`confidence = l`); статические источники, помеченные FIRMS (`type = 2`, есть
   только в архиве SP); точки ближе 500 м к постоянному тепловому источнику из
   маски `configs/persistent-sources/krasnodar_adygea.geojson` (лежит в репозитории).
3. **События.** Оставшиеся точки ближе 1 км друг к другу и с разницей дат не
   больше 2 дней объединяются в событие; вокруг его точек строится прямоугольный
   буфер 3 км.
4. **Пара снимков на событие.** До — последний снимок в 60 днях до первой
   детекции; после — в 45 днях после последней, не позже сегодняшнего дня.
   Облачность (SCL 3, 8, 9, 10) и «нет данных» (SCL 0, 1) считаются над буфером,
   пределы 30 % и 10 %. Проверяются до 12 ближайших дат с каждой стороны — всё окно поиска.
   Из пригодных снимков пара выбирается так: сначала надёжная по разрыву (не больше
   15 дней), среди них — менее облачная (шаг сравнения 5 %), затем более короткая; если
   надёжной пары нет — самая короткая. Облачная часть всё равно заштрихована и не
   оценивается, а лишние недели между снимками превращают убранные поля в «гарь».
   У снимков выбранной пары проверяется дымка, которую маска SCL не отмечает: если
   5-й процентиль синего канала B2 на ясных по SCL пикселях выше
   `scenes.haze_dark_b2` (0,04), снимок отбрасывается (`rejected_scenes[].reason =
   "haze"`) и пара выбирается заново. В ясную погоду тёмные объекты (вода, густая
   зелень, тени) в синем канале темнее; под дымкой NBR падает как на гари. Тот же
   признак исключает задымлённые промежуточные снимки из проверки «когда поле
   потемнело».
   Если между снимками больше 15 дней, у пары `reliable: false` и в `limitations`
   объясняется, что площадь гари, вероятно, завышена уборкой и вспашкой.
5. **Модель гари** запускается только в плитках буфера; результат обрезается
   буфером и областью запроса. Гарь должна быть там, где спутник видел огонь:
   вокруг каждой термоточки берётся круг размером с пиксель VIIRS (375 м), и
   детекция подтверждена, если модель видит гарь хотя бы на четверти круга.
   Остаются только связные пятна гари, пересекающие подтверждённые детекции;
   изменения на соседних полях гарью не считаются, их площадь — в
   `discarded_far_from_fire_ha`. Если ни одна детекция события не подтверждена,
   событие получает статус `no_scar`: огонь зафиксирован, гари на снимках нет
   (тление, мелкий огонь, гарь меньше пикселя VIIRS). Если все детекции ночные
   и слабее 5 МВт, в `limitations` появляется оговорка о вероятном тлении. Обрабатываются 10 крупнейших событий запроса;
   буферы соседних событий могут перекрываться, и пиксель гари относится только к
   более крупному событию, чтобы площадь не считалась дважды.

Статусы в `prediction.status` и `prediction.events[].status`:

| статус | значение |
| --- | --- |
| `ok` | гарь оценена хотя бы для одного события |
| `no_fire_evidence` | подтверждённых очагов нет; гарь не оценивалась |
| `insufficient_data` | очаг есть, но нет пригодной пары снимков (`reason`: `no_pre_scene`, `no_post_scene`, `too_cloudy`, `event_too_large`); отброшенные снимки — в `rejected_scenes` |
| `source_unavailable` | FIRMS или Copernicus не ответили; это не «пожара нет» |
| `not_processed` | событие сверх лимита `max_events` |
| `no_scar` | огонь зафиксирован, но гари в местах детекций на снимках нет |

`prediction.burn_area_reliable_ha` и `burn_area_unreliable_ha` делят площадь
гари по надёжности пары снимков (разрыв не больше 15 дней или больше).

Каждое событие содержит `fire_evidence` (`n_points`, `first_detected`,
`last_detected`, `max_frp_mw`), `buffer`, `pair` (`pre`, `post`, `cloud_pre`,
`cloud_post`), `observed_fraction`, `burn_area_ha` и `limitations` — человеческие
оговорки (разрешение VIIRS, разрыв между снимками, некалиброванные пороги,
отсутствие маски постоянных источников). У каждого контура гари есть `event_id`
и `fire_evidence`. Термоточки, подтвердившие событие, возвращаются в `hotspots`.
`prediction.evidence` объясняет отбор: сколько точек получено, принято и почему
отброшено.

**Надёжность.** Событие с гарью получает `reliability`: `reliable` или
`unreliable` с причинами в `reliability_reasons` — разрыв между снимками больше
15 дней (за это время убирают и вспахивают поля) или все детекции ночные и
слабее 5 МВт (вероятно тление). У контуров то же поле `reliable`; ненадёжные
рисуются бледно пунктиром. `prediction.burn_area_reliable_ha` — главная цифра
интерфейса, `burn_area_unreliable_ha` показывается отдельно.

**Площадь по типам земель.** `events[].burn_by_landcover_ha` и
`prediction.burn_by_landcover_ha` (`reliable` и `all`) — гектары по классам ESA
WorldCover (лес, кустарник, травяные угодья, пашня, водно-болотные…) и степеням
1–3. Это основа оценки ущерба; денежная оценка не делается.

**Промышленные объекты.** Для каждого события Overpass API OpenStreetMap ищет в
500 м от точек огня промзоны, НПЗ, факелы, трубы, электростанции, свалки и
очистные. Найденное — в `industrial_context` и в `limitations` («огонь может быть
техногенным»); событие не исключается. Ответы кешируются в `artifacts/osm-cache/`.

**Когда поле потемнело.** Между снимками «до» и «после» бывают недели, и за это время
поля убирают и вспахивают. Снимки между ними отвергнуты для пары облачностью, но над
частью пикселей ясны; с каждой стороны от огня их смотрится до
`scenes.timing_check_scenes` (по умолчанию 3), от ближайшего к огню. Пиксель гари
гарью не считается, если:

- на последнем ясном снимке **до** огня он уже был тёмным: падение NBR от этого снимка
  до снимка «после» ниже порога контура — поле убрали или вспахали раньше пожара;
- на первом ясном снимке **после** огня он ещё не был тёмным: падение NBR от снимка «до»
  до этого снимка ниже порога — поле потемнело позже, не от огня.

Маска облаков на промежуточных снимках расширяется на `scenes.timing_cloud_buffer_m`
(200 м): у края облака дымка, которую SCL не отмечает, завышает NBR, и гарь выглядела бы
«ещё не потемневшей». Порог — тот же, что у правила гари для типа земли. Итог — в `events[].pre_fire_check` и
`events[].post_fire_check`: `scenes` (использованные даты), `candidate_scenes`,
`checked_share` (доля пикселей гари, для которых нашёлся ясный снимок), `removed_ha`,
`error`; в `limitations` — сколько гектаров убрано или что проверить было нечем.

**Убрано или выжжено.** Огонь оставляет уголь: синий и зелёный каналы темнеют. У
сгоревшей зелени (зелёный рис, камыш) красный канал может посветлеть — уходит
хлорофилл, — поэтому по одному красному не судим. Солома и стерня после уборки ярче и
зелени, и угля во всех трёх видимых каналах. Пиксель гари, у которого B2, B3 и B4
посветлели больше `scenes.harvest_brightening` (0,02 — две типичные погрешности
отражения L2A), гарью не считается; это делается до проверки «когда поле потемнело» и
до проверки мест детекций. Итог — `events[].harvest_check`: `performed`, `passed`
(уборкой оказалось не больше `scenes.harvest_pass_share` = 0,35 изменений в буфере), `removed_ha`,
`removed_share`, `removed_by_landcover_ha`, `near_points` — то же в кругах вокруг самих точек огня
(`burned_ha`, `removed_share`, `confirmed`). Порог 0,35 — из 20 пожаров CLMS: у настоящих пожаров
проверка срезала не больше 0,31 в буфере и 0,33 у точек
(`experiments/validation/point-signals.json`), округлено вверх. На картинке «Снимки до/после» вырезанное показано отдельным
слоем «убрано проверкой потемнения».

**Граница зоны поиска.** `events[].buffer_edge` — доля внешнего обвода гари (пятна,
разделённые валиками и дорогами до 50 м, сливаются), лежащая на границе буфера вокруг огня
внутри выбранной области; край самой области не считается. От `events.buffer_edge_share`
(10 %) и выше зона поиска расширяется по шагам `events.expand_buffer_m` (6 и 9 км, пока
плиток не больше `max_tiles_per_event`) и событие пересчитывается с той же парой снимков:
итог — `events[].buffer_expansion` (`steps`, `closed`, `final_buffer_m`). Замкнулся контур —
граница не причина ненадёжности; упирается и в расширенную зону — гарь продолжается по
соседним полям, событие ненадёжно.

**Площадь на точку.** `events[].area_per_point_ha` — площадь гари на одну термоточку FIRMS
(после раздела площади между соседними событиями). Выше `events.max_area_per_point_ha`
(40 га — максимум у подтверждённых событий 20 пожаров CLMS, 39,8 га) событие ненадёжно:
гарь, вероятно, растеклась по соседним полям.

**Надёжность.** Событие надёжно, только если одновременно: разрыв между снимками не
больше 15 дней; не слабый ночной огонь; проверка «убрано или выжжено» проведена и
пройдена; контур замкнут в зоне поиска (с расширением); площадь на точку не выше 40 га.
В сезон уборки (`events.harvest_season_months`, сентябрь–октябрь) событие на пашне и
водно-болотных угодьях (рисовые чеки) надёжно, только если проверка подтвердила гарь у
самих точек огня (`harvest_check.near_points.confirmed`); иначе — «требует подтверждения»
(в интерфейсе — «гарь оценена · требует подтверждения»).

**Погода.** `events[].weather` — погода Open-Meteo в центре события на время первой
детекции: `temperature_c`, `humidity_pct`, `wind_speed_ms`, `wind_gusts_ms`,
`wind_from` и `spread_to` (румбы), `precip_24h_mm`, показатель Нестерова `nesterov`
(Σ t·(t − td) в 13 ч по дням без дождя больше 3 мм за 30 дней) и класс
`danger_class` 1–5 (до 300, 1000, 4000, 10000 и выше), `source`, `cell` (ячейка 0.1°).
Последние ~3 месяца — оперативные модели погоды, раньше — реанализ ERA5. При сбое —
`{"error": …}`, расчёт гари не прерывается. Ответы кешируются в
`artifacts/weather-cache/`. Оповещения мониторинга получают то же поле `weather` на
время последней детекции.

**Даты.** Дата контура — начало пожара (первая детекция); даты снимков — в
`pre_image_date` и `post_image_date`.

**Кеш на диске.** Ответ режима сохраняется в
`artifacts/satellite-cache/fire-first-results/`; повтор того же участка и периода
отвечает мгновенно и без сети. Ключ включает версию логики, конфиги и маску —
после их изменения расчёт повторяется. Если после периода ещё могут появиться
снимки, запись живёт сутки. Снимки, прогноз и маска вырезанного проверкой «убрано
или выжжено» сохраняются в `annotation-scenes/<ключ>/` для картинки «Снимки до/после».

**Реальные случаи.** `configs/demo_cases.yaml` — области и периоды реальных
событий края; `GET /api/demo-cases` отдаёт их интерфейсу (кнопки «Реальные
случаи»). Результат считает сервис обычным запросом;
`python scripts/warm_demo_cases.py --output experiments/validation/demo-cases.json`
заранее заполняет кеш.

Прежнее поведение (модель по всему участку до ~20 км) — `fire_first: false` в
теле `POST /api/query` или параметре `GET /api/query`. В режиме fire-first область
может быть до 60 км по стороне: модель работает только в буферах событий.

Маска постоянных источников края лежит в репозитории; отсутствующую сервис строит при
первом запуске в фоне (`service/persistent_mask.py`, нужен `FIRMS_MAP_KEY`, `FIRES_BUILD_MASK=0`
отключает; состояние — `/api/health` → `fire_first.persistent_mask`). Вручную (раз в год):

```bash
python scripts/build_persistent_sources.py --region configs/regions/krasnodar_adygea.geojson \
    --output configs/persistent-sources/krasnodar_adygea.geojson
```

Источник считается постоянным, если огонь в ячейке ~400 м и её соседях
фиксировался не меньше чем в 5 разных дней и в 3 разных месяцах за последние
12 месяцев, причём хотя бы раз в декабре–феврале. Разные месяцы не дают записать
в маску один многодневный пожар, зимняя детекция отделяет круглогодичные
промышленные источники от весенних и осенних сельхозпалов.
Ответы FIRMS за прошедшие даты кешируются в `artifacts/firms-cache/` (в именах
файлов нет ключа). Все параметры — `configs/service.yaml`; путь меняется
переменной `FIRES_SERVICE_CONFIG`.

### `GET /api/health`

Состояние сервиса, источник данных, число объектов, доступный диапазон дат,
цвета и подписи степеней, лимиты.

```bash
curl http://127.0.0.1:8080/api/health
```

curl "http://127.0.0.1:8080/api/query?bbox=40.95,47.45,41.2,47.6&from=2021-01-01&to=2021-12-31"

### Мониторинг огня

Сервер сам опрашивает NASA FIRMS по районам наблюдения (`configs/service.yaml` →
`fire_first.monitor`: период опроса, окно свежести, радиус слияния). Точки проходят
те же фильтры, что и в режиме «огонь прежде гари» (достоверность, статические и
постоянные источники), и группируются в очаги. Новый очаг — новое оповещение; новые
точки рядом с недавним очагом дополняют его («огонь продолжается»). Состояние —
`artifacts/monitor/state.json`. Фоновый опрос выключается переменной `FIRES_MONITOR=0`.
Промышленные объекты OpenStreetMap в мониторинге не проверяются (лимиты Overpass) —
только при оценке гари очага.

```bash
curl http://127.0.0.1:8080/api/monitor                                   # районы, оповещения, непрочитанные
curl -X POST http://127.0.0.1:8080/api/monitor/zones -H "Content-Type: application/json"      -d '{"name": "Анапа", "bbox": [37.1, 44.85, 37.6, 45.2]}'            # район + сразу проверка
curl -X POST http://127.0.0.1:8080/api/monitor/check                     # проверить все районы сейчас
curl -X POST "http://127.0.0.1:8080/api/monitor/alerts/read"             # все прочитаны (или ?alert_id=…)
curl -X DELETE http://127.0.0.1:8080/api/monitor/zones/<id>
```

### Выгрузки

```bash
Q="bbox=40.95,47.45,41.2,47.6&from=2021-01-01&to=2021-12-31"

curl -o burns.geojson    "http://127.0.0.1:8080/api/export/burns.geojson?$Q"
curl -o hotspots.geojson "http://127.0.0.1:8080/api/export/hotspots.geojson?$Q"
curl -o report.json      "http://127.0.0.1:8080/api/report.json?$Q"
curl -o report.csv       "http://127.0.0.1:8080/api/report.csv?$Q"
curl -o fires.kml        "http://127.0.0.1:8080/api/export/fires.kml?$Q"
# снимки одного события (event_id — из prediction.events[*].event_id)
curl -o event.png        "http://127.0.0.1:8080/api/events/<event_id>/preview.png?$Q"
```

`fires.kml` — контуры гари (по папкам: надёжная оценка и скрытая по умолчанию
ненадёжная) и точки FIRMS; открывается в Google Earth поверх спутниковой подложки.

`preview.png` — картинка 2×2 из тех же снимков Sentinel-2, по которым считалась гарь
события: до и после в естественных цветах, после в SWIR (B12-B8A-B4, гарь тёмная),
после с контуром сервиса, точками огня, буфером 3 км и облаками. Для полигона —
`POST /api/events/<event_id>/preview.png` с телом запроса.

`burns.geojson` — EPSG:4326, объявленная CRS `urn:ogc:def:crs:OGC:1.3:CRS84`,
атрибуты `id`, `severity`, `area_ha` (плюс `severity_label` и `date` для читаемости).
Параметр `?full=true` добавляет все остальные атрибуты.

`report.csv` — разделитель `;`, десятичная запятая, UTF-8 с BOM: открывается в Excel
с русской локалью без настроек импорта. Содержит блок сводки, распределение по
степеням и перечни контуров и термоточек.

Для полигональной области те же выгрузки доступны через `POST /api/export?kind=…`,
где `kind` — `burns`, `hotspots`, `report.json`, `report.csv` или `kml`, а тело совпадает
с телом `POST /api/query`.

### `POST /api/reload`

В режиме `archive` перечитывает файлы без перезапуска. В режиме `satellite`
сообщает, что новые снимки выбираются при следующем запросе новой области.

### Ошибки

`400` с `{"detail": "..."}` — некорректная область, период или их комбинация.
`422` — тело запроса не проходит схему. `503` — недоступны снимки, модель или
другой нужный источник данных (в режиме `archive` — каталог GeoJSON).

## Учётные записи и наблюдаемые области

Карта, запросы, выгрузки и сохранение области работают **без входа**. У гостя
области сохраняются в `sessionStorage` текущей вкладки и не отправляются в базу.
Учётная запись нужна для постоянного хранения областей на сервере.

Хранилище — SQLite из стандартной библиотеки, файл `service/data/service.sqlite3`
создаётся при первом запуске. Пароли хешируются `hashlib.scrypt`, сессия — случайный
токен в куке `HttpOnly` сроком на 30 дней. Внешних пакетов для этого не требуется.

Это учебный прототип на локальном сервере по HTTP. Пароль от других сервисов сюда
вводить не следует. Под HTTPS включите `FIRES_SECURE_COOKIES=1`.

```bash
# регистрация; сессия приходит в куке
curl -c cookies.txt -X POST http://127.0.0.1:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"login":"inspector","password":"gorenie2026"}'

curl -c cookies.txt -X POST http://127.0.0.1:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"login":"inspector","password":"gorenie2026"}'

curl -b cookies.txt http://127.0.0.1:8080/api/auth/me
curl -b cookies.txt -X POST http://127.0.0.1:8080/api/auth/logout
```

Логин: от 3 до 32 символов, латиница, цифры, точка, дефис, подчёркивание.
Пароль: не короче 8 символов.

### Область под наблюдением

```bash
# сохранить область
curl -b cookies.txt -X POST http://127.0.0.1:8080/api/areas \
  -H "Content-Type: application/json" \
  -d '{"name":"Сальские степи","from":"2021-01-01","to":"2021-12-31","bbox":"40.0,46.9,41.3,47.6"}'

curl -b cookies.txt http://127.0.0.1:8080/api/areas
curl -b cookies.txt -X DELETE http://127.0.0.1:8080/api/areas/1

# актуальный статус и что изменилось с прошлого раза
curl -b cookies.txt "http://127.0.0.1:8080/api/areas/1/status"
```

Ответ `status` повторяет `/api/query` и добавляет два поля:

```jsonc
{
  "data_updated_at": "2026-09-18T20:41:17+00:00",
  "changes": {
    "first_visit": false,
    "hotspots": 1,
    "burns": 0,
    "area_ha": 0.0,
    "data_changed": true,
    "nothing_new": false
  }
}
```

Область запоминает, что пользователь уже видел, поэтому `changes` показывает прирост
с прошлого просмотра. Просмотр записывается автоматически; `?remember=false` позволяет
посмотреть статус, не сдвигая отметку.

Чужая область недоступна: запрос к ней возвращает `404`, а не данные владельца.
Предел — 50 областей на пользователя.

**Откуда берётся актуальность.** В режиме `satellite` сохранённая область при
открытии получает прогноз по выбранным снимкам. Результат повторного запроса
той же геометрии и дат кешируется в памяти процесса. Для нового периода или
области снимки запрашиваются заново. В режиме `archive` сервис следит за
изменением файлов GeoJSON и перечитывает их.

## Живой слой NASA FIRMS

Оперативные детекции активного горения VIIRS с задержкой около трёх часов:
Suomi NPP, NOAA-20, NOAA-21. Это отдельный слой наблюдений FIRMS.

Нужен бесплатный ключ: <https://firms.modaps.eosdis.nasa.gov/api/area/> — форма
«Get MAP_KEY», ключ приходит на почту сразу.

```bash
export FIRMS_MAP_KEY=ваш_ключ        # PowerShell: $env:FIRMS_MAP_KEY="ваш_ключ"
python -m service
```

```bash
# только живые точки
curl "http://127.0.0.1:8080/api/live?bbox=39.0,45.0,45.5,49.5&days=1"

# вместе с прогнозом по снимкам
curl "http://127.0.0.1:8080/api/query?bbox=42.0142847,46.4152428,42.0342847,46.4352428&from=2024-07-06&to=2024-07-19&live=true"
```

Ответ содержит блок `live`:

```jsonc
{
  "available": true,
  "count": 14,
  "fetched_at": "2026-09-18T20:41:33+00:00",
  "sources": ["VIIRS_SNPP_NRT", "VIIRS_NOAA20_NRT", "VIIRS_NOAA21_NRT"],
  "day_range": 2,
  "latency_note": "Задержка NASA FIRMS около 3 часов",
  "error": null,
  "hotspots": { "type": "FeatureCollection", "features": [] }
}
```

Без ключа или при недоступной сети слой выключается, `available` становится `false`,
а `error` объясняет причину. Запрос при этом не прерывается: карта продолжает
показывать прогноз гарей. В интерфейсе переключатель слоя приглушён
с подсказкой, а не ломается молча.

Ограничения источника, учтённые в коде: не больше 5 суток за запрос, лимит ключа
5000 обращений за 10 минут (ответы кэшируются на 5 минут), пустой CSV с одним
заголовком означает «детекций нет», а не ошибку.

**Контуры гарей в реальном времени невозможны.** Sentinel-2 возвращается на одну точку
раз в пять дней, плюс время на обработку. Живым может быть только первый этап —
активное горение.

## Формат данных

Каталог с любым числом файлов `*.geojson`. Объекты разделяются по свойству `kind`:
`active_fire` — термоточка (Point), `burn_severity` — контур гари (Polygon/MultiPolygon).
Если `kind` нет, тип определяется по геометрии. Короткие имена `af` и `bs` из версии
ML-части до переименования тоже распознаются.

Термоточка:

```json
{
  "type": "Feature",
  "geometry": {"type": "Point", "coordinates": [41.061803, 47.550767]},
  "properties": {
    "kind": "active_fire",
    "chip_id": "af_rostov_2021_07",
    "point_id": "AF-ROSTOV-2021-07-01",
    "date": "2021-07-22",
    "satellite": "Suomi NPP",
    "instrument": "VIIRS",
    "confidence": "high",
    "frp_mw": 58.2,
    "region": "Ростовская область"
  }
}
```

Контур гари:

```json
{
  "type": "Feature",
  "geometry": {"type": "Polygon", "coordinates": [[[41.02, 47.53], "..."]]},
  "properties": {
    "kind": "burn_severity",
    "chip_id": "bs_rostov_2021_07",
    "contour_id": "BS-ROSTOV-2021-07",
    "date": "2021-07-26",
    "class_id": 3,
    "area_ha": 1335.82,
    "source": "Sentinel-2",
    "region": "Ростовская область"
  }
}
```

Обязательны только дата и — для контура — степень поражения. Остальное имеет запасные
варианты:

| поле сервиса | берётся из | если нет |
|---|---|---|
| `id` | `id`, `contour_id`, `point_id`, `feature_id`, `chip_id` | генерируется из имени файла и номера |
| дата | `date`, `acq_date`, `acq_datetime`, `date_post`, `observed_at` | ошибка 503 |
| `severity` | `severity`, `class_id` | ошибка 503 |
| `satellite` | `satellite`, `platform` | `"не указан"` |
| `instrument` | `instrument`, `sensor` | `"VIIRS"` |
| `source` | `source`, `mission` | `"Sentinel-2"` |

`area_ha` из файла не используется: площадь всегда пересчитывается по обрезанной
областью геометрии.

### Площадь

Считается в метрической проекции, не в градусах. Проекция выбирается один раз по
области запроса и применяется ко всем контурам, чтобы цифры в справке складывались:
UTM-зона по центру области, а для областей шире одной зоны (>6°) или за пределами
±80° широты — равновеликая EPSG:6933. Выбранная проекция возвращается в
`summary.metric_crs` и попадает в CSV.

## Режим archive: готовые прогнозы

Режим `archive` показывает заранее подготовленные GeoJSON из каталога (формат — раздел
«Формат данных»), без обращения к внешним API:

```bash
python -m service --data-dir путь/к/каталогу
```

Или через переменные: `FIRES_DATA_DIR=путь/к/каталогу FIRES_QUERY_MODE=archive python -m service`.
Проверить, что подхватилось: `curl http://127.0.0.1:8080/api/health` — поле
`source.kind` станет `files`, в `source.files` будут имена прочитанных файлов.

## Структура

```text
service/
  __main__.py          python -m service
  app.py               FastAPI: маршруты, обработка ошибок, раздача интерфейса
  config.py            настройки, подписи и цвета степеней
  fire_evidence.py     термоточки FIRMS, фильтры, маска постоянных источников, события, OSM
  fire_first.py        «огонь прежде гари»: пара снимков, модель, проверки, надёжность
  event_preview.py     картинка «Снимки до/после» события
  monitor.py           районы наблюдения и оповещения
  weather.py           погода Open-Meteo и показатель Нестерова
  satellite.py         прежний режим: модель по всему участку
  db.py, auth.py       SQLite: пользователи, сессии, наблюдаемые области
  live.py              живой слой NASA FIRMS
  geocode.py           поиск мест (Photon / OpenStreetMap)
  llm.py               текстовый разбор справки через LLM-провайдера (по ключу)
  sources.py, geo.py, query.py, export.py
  web/                 интерфейс: index.html, styles.css, app.js, dashboard.js, monitor.js
src/                   правило гари (dNBR по типу покрова) и доступ к Copernicus Data Space
configs/               burn_model.yaml, service.yaml, demo_cases.yaml, regions/
scripts/               маска постоянных источников, проверки на CLMS, прогрев реальных случаев
tests/                 unittest
```

Интерфейс — чистые HTML/CSS/JS и Leaflet с CDN, без сборки. Диаграмма в справке
нарисована вёрсткой, дополнительных библиотек нет.

Подложки: OSM в тёмной палитре (CSS-фильтр), OSM в исходном виде и спутниковые
снимки Esri World Imagery. Все три работают без ключей API.
